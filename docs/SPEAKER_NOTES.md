## Slide 1: Project Information

Introduce the project and the team. StudyMate is a single-user academic planning assistant for one student: courses, attendance, grades, study time and pocket money in one place, with transparent calculations, a rule-based study planner and a machine-learning risk estimate. This is the 25% mid-evaluation: today we show the foundation (requirements, design, database, backend, frontend, analytics), and we are explicit about what is not built yet. Presenters: Haifa A. ## Slide 2: Overview of the FYP

What it is: a single-user academic planning assistant. The problem: students track deadlines, attendance rules, CGPA targets and pocket money in different places, and no tool connects them or looks ahead. Objectives: transparent GPA/CGPA/attendance calculations, what-if simulators and a target-GPA planner, a rule-based study plan, and an ML risk prediction. Architecture: four layers - React front end, Express API that holds authentication, CRUD, the analytics engine, the planning engine and chat orchestration, a separate FastAPI service for the ML model and an LLM API used only to explain results, and PostgreSQL for data. Key design rule: AI/ML is limited to risk classification and chat explanations; GPA, attendance and planning are deterministic rules. The system keeps working if the ML or chat service is down.

## Slide 5: Problems and Challenges

Challenges that are genuinely relevant at this stage. 1) The proposal refers to the institutional grade-point scale but does not list it; we put the scale in a single configuration file with an assumed 4.0 scale and will confirm it with university policy. 2) Dataset: no dataset is selected yet and public datasets come from other educational contexts, so predictions will be estimates; we will compare candidate datasets and models and prioritise High-risk recall, without promising a fixed accuracy. 3) Consistency: we use one SQL schema as the source of truth and trace requirement IDs to endpoints and tests; this exposed small gaps, for example the ERD had no instructor attribute although the scope requires one. 4) Calculation edge cases: testing found that a what-if simulation with no recorded classes showed a misleading 0%; it was fixed and covered by a unit test; every result shows its formula and working. 5) ML integration: the model will live in a separate FastAPI service called with a timeout so a failure never breaks the rest of the application; this is tested for the status check. 6) Scope: eleven modules for two members in twelve months, so we built the foundation first and keep ML and chat isolated. Closing: next steps are dataset selection, the study planner and the risk model.
